# Brownfield PRD prompt (fill `wow/pb/prd.md` so Product Brain scores 100%)

> **Legado (deprecado):** solo aplica a `wow pack prd|rfc --full`. El camino por defecto es el paquete de registro,
> que sale completo de `wow pack prd|rfc` y no necesita este prompt.

Evidence: `reference/product-brain/README.md` (Product Brain backend read at commit 9b19a89). In short:
- Product Brain's backend computes completion; the model does not. Any non-empty text fills a field, including
  `[SIN DEFINIR] …` and `No aplica: …`. A remaining `{{placeholder}}` is empty.
- Each table counts as one unit, filled by one complete row.
- `open_questions` needs question, owner and status on every row.
- The template is marketplace-shaped (buyer/seller rows); Product Brain's own example is a marketplace.

---

## Prompt (Claude Opus or Codex, with the repositories and the context pack available)

You are completing the PRD of a change to an EXISTING system. The file `wow/pb/prd.md` was generated by
`wow pack prd` from Product Brain's real template: some fields are already filled from the plan, the rest are
`{{placeholders}}`. Product Brain will map this document field by field and score it. Fill every placeholder
with true content; when information is missing, write an explicit undefined marker instead of a guess.

INPUTS (the only sources of truth):
- `wow/context-pack/facts.md`, `metrics.md`, `decisions.md`, `contracts.md` and `pending-owner.md`: claims tagged
  [MEDIDO], [ESTIMACIÓN] or [SIN DEFINIR], each with `fuente: path:line`.
- `wow/plan/PLAN.md` (Brief) and `wow/plan/manifest.json` (epics, stories, acceptance criteria).
- `.spec-kit/discovery/architecture.md` (Spec-Kit discovery of the real system) and the code itself.

RULES:
1. Output Spanish (professional, neutral Rioplatense).
2. Edit `wow/pb/prd.md` in place: replace every `{{placeholder}}`. Never rename, reorder or remove headings,
   tables or columns, and keep the first line (the `wow:` header comment).
3. Brownfield framing:
   - "Contexto" describes the current system in 4–8 lines, citing paths in backticks.
   - "Problema" is the measured pain, with numbers, frequency and today's workaround.
   - Baselines are [MEDIDO] values, with where, when and how they were measured.
   - The PRD says WHAT changes and WHY; HOW belongs to the RFC.
4. Missing information: `[SIN DEFINIR] — <qué falta y quién lo decide>` in the field, plus a row in
   "Preguntas Abiertas". Never write a plausible number, owner, date, SLA or provider.
5. Slots that do not apply (buyer/seller impact, a third user type that does not exist):
   `No aplica: <motivo concreto>`. Never reshape the domain to fit the template.
6. Tables: one row per real item, at least one complete row. Delete unused template rows instead of
   padding them; every kept row has all its columns filled.
7. KPIs:
   - the North Star goes in the first row;
   - Baseline is the measured value with its tag;
   - Target and Plazo are the owner's decision or `[SIN DEFINIR] — decide el owner`.
8. Preguntas Abiertas: Owner is the deciding ROLE ("Owner de producto", "Tech Lead de <equipo>"), never an
   invented person; Estado is `Abierta`. Every unchecked item of `pending-owner.md` appears here.
9. Keep the acceptance ids (`AC1`, `E1.C1`) verbatim.
10. Self-contained: no "ver documento X" without its content; cite files next to the content they support.
11. Run `wow pack check prd` and fix the packet until it exits 0. Then go through the CHECKLIST; do not print it.

FIELD GUIDANCE:
- `author`, `vertical`, `quarter_year`, `priority`: from the owner or `[SIN DEFINIR] — decide el owner`.
- `why_now`: the measured cost of the current situation.
- Users: the real roles of THIS system. If only two exist, write `No aplica: el sistema tiene dos roles (<rol 1>, <rol 2>)`
  in every cell of the third block.
- `impact_buyer_experience` / `impact_seller_ops`: `No aplica: <sistema> no es un marketplace; el impacto equivalente
  está en <fila real>`, unless the domain truly has buyers and sellers.
- Risks: probability and impact as Alta/Media/Baja; include coexistence with and migration from the current system.
- NFR: compatibility with existing contracts and data, observability already in place, cost limits.
- Dependencies: the real teams or services touched; Referente is a role; Estado is `Confirmada` or `Pendiente`.

CHECKLIST (Product Brain's Phase 3 plus the brownfield gates):
- [ ] `wow pack check prd` exits 0.
- [ ] The problem has numbers, frequency and impact, and cites where they were measured.
- [ ] Users are real roles with jobs-to-be-done; non-applicable blocks say `No aplica: …`.
- [ ] The North Star row exists; its baseline is tagged; target and deadline are decided or `[SIN DEFINIR]`.
- [ ] Secondary KPIs are measurable; In-Scope is the MVP; Out-of-Scope rows have a reason and a "cuando".
- [ ] Requerimientos Clave are verifiable and keep the AC/E ids; a Tech Lead can derive stories from them.
- [ ] Risks have probability, impact and mitigation; assumptions are written as assumptions.
- [ ] Main flows mention the happy path plus at least two edge cases (empty input, volume, concurrency, outage).
- [ ] Every `[SIN DEFINIR]` has its row in Preguntas Abiertas, with an owner role and `Abierta`.
- [ ] No marketplace, comprador/vendedor, SLA, API Gateway, Okta/OAuth, circuit breaker, owner name or date that is
      not in the inputs.

## How to paste it in Product Brain

1. Create a PRD document using the base template "PRD" (a customised copy may have different fields).
2. First message: `wow/pb/preamble.md`. Second message: "Comparto el PRD ya redactado sobre un sistema existente;
   mapealo campo por campo a la plantilla sin resumir", followed by the packet.
3. If the agent insists on Phase 1 Discovery, confirm its summary with "dale".
4. Trust only the backend line `**Completitud del documento:** N%`; answer just the fields it lists as pending.
5. Copy the whole chat to `wow/pb/chats/prd.md` and run `wow pbchat audit prd --deep`.
